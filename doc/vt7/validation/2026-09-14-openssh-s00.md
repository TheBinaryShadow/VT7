# OpenSSH S00 architecture evaluation

Evaluation date: 2026-09-14. Status: complete. The endpoint-independent
preflight and controlled Debian-server network package are accepted on Windows
7. Raw non-PTY bytes, strict trust, key authentication, negotiated algorithms,
initial PTY dimensions, cancellation and exit drain are characterized. The
exact Microsoft 10.0p2 source explains the observed 0 by 0 PTY: unmodified
redirected `ssh.exe` cannot obtain or receive VT7's console dimensions. S00
therefore rejects it as VT7's first-class interactive SSH backend. It remains a
proven option for non-PTY command transport. No unchanged rerun is requested.

## Candidate and licensing boundary

The current official Microsoft release is Win32-OpenSSH
`10.0.0.0p2-Preview`. The official release labels it preview/non-production and
publishes `OpenSSH-Win64.zip`, 5.44 MB, with SHA256
`23F50F3458C4C5D0B12217C6A5DDFDE0137210A30FA870E98B29827F7B43ABA5`.
Its notes identify OpenSSH 10.0p2, LibreSSL 4.2.0 and current hybrid
post-quantum key exchanges. The project installation instructions continue to
state that GitHub releases can be installed on Windows 7 and later.

OpenSSH is not uniformly MIT licensed. Its official license file describes a
mixture of BSD, ISC, MIT-style and public-domain terms and states that it
contains no GPL code. These terms are permissive and compatible with an MIT
VT7 codebase when their notices are retained, but a bundled distribution would
contain another license family. The project owner has said the target machine
already has OpenSSH under `C:\Program Files\OpenSSH` and on `PATH`. This first
diagnostic therefore treats it as an external installed executable, records its
identity and does not copy or redistribute any OpenSSH file. The later standing
permissive-license policy would allow exact OpenSSH notices to be retained if a
future command-transport package ever bundles it; the rejected interactive
architecture gives VT7 no current reason to do so.

## Endpoint-independent preflight

`Test-VT7OpenSsh.ps1` accepts an explicit `ssh.exe` path plus optional expected
hash and version pattern. It launches the client with `UseShellExecute=false`
and captures stdout and stderr from their raw base streams into separate binary
files. It records every command, exit code, byte count and channel SHA256.

The preflight performs these bounded checks without SSH credentials or a server:

1. Capture `ssh -V` and require its successful version response to use stderr
   only.
2. Capture the supported key-exchange, cipher, MAC and key lists and require
   them to use stdout only.
3. Run `ssh -G` with `-F NUL`, disabled canonicalization and explicit NUL
   known-host paths, retaining the effective configuration.
4. Open a disposable listener on an ephemeral IPv4 loopback port, accept the
   client's connection without sending an SSH banner, terminate the client
   after 750 milliseconds and require bounded process exit before five seconds.

The script does not install a service, open a firewall rule or change machine,
user SSH or known-host configuration. The target runner verifies every packaged
file through an in-process SHA256 implementation before discovering
`C:\Program Files\OpenSSH\ssh.exe`, falling back to `ssh.exe` on `PATH`.

The local PowerShell 7 run passes. The exact packaged batch also passes through
`cmd.exe` and Windows PowerShell 5.1 from a path containing spaces. It records
the inbox 9.5 client, separate raw channels and bounded stalled-peer
cancellation in 812 milliseconds. Authenticode status is informational: the
development Windows PowerShell 5.1 environment could not autoload its Security
module, so package 0.2 records that status as unavailable without weakening the
required hash identity. Package 0.1 exposed this optional-module dependency
before issue; that unissued candidate was deleted.

## Supplied Windows 7 result

Two consecutive runs completed on Microsoft Windows NT 6.1.7601 Service Pack 1,
x64 OS and process, Croatian `hr-HR` culture, English `en-US` UI culture and
Windows PowerShell 5.1.14409.1005. Both selected
`C:\Program Files\OpenSSH\ssh.exe` and reported
`OpenSSH_for_Windows_10.0p2 Win32-OpenSSH-GitHub, LibreSSL 4.2.0`, file version
10.0.0.0 and product version `OpenSSH_10.0p2 for Windows`.

The executable is 1,352,760 bytes with SHA256
`6890C128C86CC2C38AAD9FCB32A82B851FF3D38C714A1F656B8E445D7CD5E1C6`.
Its Authenticode signature is valid and names Microsoft Corporation. A
transient independent comparison found the same path, size and SHA256 for
`OpenSSH-Win64/ssh.exe` inside the official 5,704,583-byte x64 archive whose
SHA256 is the published
`23F50F3458C4C5D0B12217C6A5DDFDE0137210A30FA870E98B29827F7B43ABA5`.

The two runs have 22 files and 17,779 bytes each. Their version output,
algorithm inventories, effective configuration, warning bytes and expected
empty channels match. The inventories contain 15 key exchanges, 10 ciphers,
16 MACs and 14 key types. Capability inventory includes modern hybrid key
exchange entries; the isolated effective defaults exclude the listed SHA-1 key
exchanges and CBC ciphers. `ssh -Q` remains a capability inventory, not evidence
that every listed algorithm is enabled by default.

Both stalled-peer cases accepted the loopback connection, requested
cancellation and exited without reaching the five-second timeout, in 807 and
808 milliseconds. Version output uses stderr only and algorithm inventories use
stdout only. Effective configuration uses stdout, while stderr contains the

is not a terminal.` The effective default is `requesttty auto`. Therefore the
network phase must test `-T` exact-byte transport separately from forced `-tt`

window-change question.

The endpoint-independent Windows 7 preflight is accepted. It selects no shipping
architecture and requests no unchanged rerun. The two raw runs are archived
byte-identically as 44 files and 35,558 bytes, with every copied file compared
by SHA256. See the [archive verification](../../../artifacts/vt7/evidence/openssh-s00-win7-preflight-0.2/ARCHIVE-VERIFICATION.json)

## Controlled-server experiment

The controlled-server package uses that exact recorded client against the
owner's Debian 12 Bookworm server with bash, `/bin/sh`, `stty` and
`/usr/bin/python3`. It keeps secret material outside the evidence and tests:

- unknown, accepted and changed host-key paths, with client diagnostics kept
  separate from remote terminal bytes;
- non-PTY exact UTF-8/VT fixture bytes and PTY output with echo/newline behavior
  controlled explicitly;
- the initial remote PTY rows and columns;
- an actual SSH window-change request after a grid resize, never resize text
  typed into shell input;
- public-key and passphrase/prompt ownership without scraping arbitrary remote
  output as authentication UI;
- cancellation during connection and active output, final output drain, EOF and
  process exit ordering.

The official Win32-OpenSSH TTY/PTY notes state that clients before Windows 10
use a built-in VT100 interpreter for console TTY sessions and explicitly do not
extend it to VT100+ behavior. The same notes record console resize limitations.
That makes ordinary interactive-console success insufficient for VT7. The
network diagnostic tests the redirected `-T` channel for unchanged bytes and
the forced `-tt` path separately. An actual VT7-driven SSH window-change request
remains a distinct control-path proof.

The issued diagnostic is `VT7-OpenSSH-S00-Network-0.1-x64.zip`, 16,203 bytes,
SHA256
`8029CC9CF48F9BAEA839F16F3E104A552F848AB17A4A12636C966145B421B7FA`,
with eight verified top-level files and no EXE, DLL, MSI, private key or OpenSSH
file. Its Windows PowerShell 5.1 package verification passes before and after
ZIP extraction; an altered README is rejected.

The runner requires an independently obtained Ed25519 server host-key
fingerprint, then checks the scanned key before authentication. It exercises
unknown and changed-key rejection, key-only `BatchMode` authentication,
negotiated algorithms, exact binary stdout/stderr plus remote exit 23, a
131,071-byte final drain plus remote exit 37, forced PTY allocation and initial
dimensions, and cancellation during active output. Raw trust, negotiation and
PTY-sensitive scratch data is deleted; retained PTY and cancellation text is
redacted.

## Supplied controlled-server result

The complete Windows 7 run uses the pinned 10.0p2 client and the owner's Debian
12 server. The independently supplied Ed25519 fingerprint matches the scanned
key. Strict unknown-host and changed-key cases both exit 255 and are rejected
before authentication. Dedicated public-key authentication succeeds with
`BatchMode=yes`, `IdentitiesOnly=yes`, the agent disabled and password fallback
disabled.

The negotiated key exchange is `sntrup761x25519-sha512`, the host key is
`ssh-ed25519`, and both directions use
`chacha20-poly1305@openssh.com` with implicit authentication and no compression.
The 89-byte non-PTY stdout fixture and 22-byte remote stderr fixture match every
expected byte, including UTF-8, VT, combining, wide, NUL and mixed newline
content. Remote exit 23 propagates. The separate 131,071-byte binary stream
drains exactly before remote exit 37; its SHA256 is
`DE222739D6EF744C5FCE51179AD6536D9D81E4F36C9694B4750336481F2A2B59`.
Active output supplies 649 bytes before cancellation completes in 757
milliseconds without reaching the timeout.

Forced `-tt` allocation makes remote stdin, stdout and stderr TTYs and sets
`TERM=xterm-256color`, but the initial remote size is 0 columns by 0 rows. This
is a concrete architecture failure for redirected unmodified `ssh.exe`: it
proves PTY allocation, but not usable initial geometry or live resize control.

Package 0.1 also disproves one of its privacy claims. The changed-host text
retained the public server host-key fingerprint and a temporary Windows profile
path. It did not retain the server hostname, SSH username, port, private key,
private-key hash or password. The raw 16-file, 149,987-byte result is preserved
byte-identically as restricted local evidence; it is not safe for publication.
A sanitized review copy removes the fingerprint and profile path. Current source
retains only diagnostic classifications, and any reissue uses package identity
0.2. The behavioral result needs no rerun.

## Exact source explanation and S00 decision

The tested binary corresponds to Microsoft openssh-portable tag `v10.0.0.0`,
commit `b8c08ef9da9450a94a9c5ef717d96a7bd83f3332`. In that exact source:

- `w32_ioctl(TIOCGWINSZ)` ignores the supplied file descriptor and calls
  `GetConsoleScreenBufferInfo(GetStdHandle(STD_OUTPUT_HANDLE))`. Redirected
  stdout is a pipe, so this query cannot provide a console size.
- `client_session2_setup` responds to that failure by sending a `pty-req` with
  zero rows and columns. This matches the target's 0 by 0 observation.
- the Windows terminal console path notices `WINDOW_BUFFER_SIZE_EVENT` while
  processing console input, queues `SIGWINCH`, and lets the client loop send the
  SSH `window-change` request. VT7 supplies redirected input bytes rather than
  Windows console input records, so this event path is absent as well.

These are architectural properties, not an unexplored timing case. A second
runtime resize package using the same redirected handles would repeat the same
limitation and is unnecessary. Windows OpenSSH can route authentication through
its console/TTY path or an `SSH_ASKPASS` helper, so a structured prompt helper is
possible. That does not repair PTY geometry.

S00 accepts the exact external client for strict-trust, key-only, non-PTY
command execution with lossless separated output and bounded cancellation. It
rejects unmodified external `ssh.exe` for VT7's interactive terminal sessions.
Full interactive SSH acceptance was left to S01, which subsequently accepted
SSH.NET 2026.0.0 with explicit PTY creation, resize, trust and authentication.

- [Windows OpenSSH TTY/PTY design](https://github.com/PowerShell/Win32-OpenSSH/wiki/TTY-PTY-support-in-Windows-OpenSSH),
  including the downlevel console path and resize constraints.

## Subsequently accepted S01 candidate and license policy

SSH.NET 2026.0.0 is the selected embedded candidate. It targets .NET Framework
4.6.2, which is load-compatible with VT7's .NET Framework 4.8 host, and exposes
explicit shell creation, `ShellStream.ChangeWindowSize`, host-key trust events,
password and keyboard-interactive authentication, encrypted private keys, and
cancelable connection APIs. Its algorithm inventory includes the negotiated
`sntrup761x25519-sha512`, `ssh-ed25519` and
`chacha20-poly1305@openssh.com` combination observed in S00.

The exact candidate is source tag `2026.0.0`, commit
`7b2fd3dbf2c86a80a7b06cea020aa5f821c9902e`. The signed NuGet package is
1,604,179 bytes with SHA256
`B2515DE616821198F5CF5530F5EA198912730BBE3504EF4C6AEE00A661FECAC2`.
An exact .NET Framework dependency audit found 13 packages. Their NuGet license
metadata is MIT, but package contents disclose additional permissive terms.
SSH.NET's third-party notices include an ISC-style BCrypt notice;
BouncyCastle.Cryptography 2.7.0 states that its compiled BZip2 portion is
Apache License 2.0; and Microsoft compatibility packages carry broad supplier
notice sets. BouncyCastle is used throughout current SSH.NET cryptography, so
removing it is not a small adapter change. The exact closure and hashes are in
the [SSH.NET license audit](../research/2026-09-14-sshnet-license-audit.md).

At S00 completion no SSH.NET or BouncyCastle file had been added to VT7,
restored by its build, executed by the application, or accepted for product
distribution. On
2026-09-14 the owner approved this permissive closure and a standing project-wide
policy allowing compatible permissive dependencies with all required license,
copyright, notice and acknowledgement material retained. VT7-authored source
remains MIT.

Subsequent S01 package 0.6 preserves the exact audited closure and supplier
notices. Its public-key-only and optional-password Windows 7 runs pass load,
negotiation, trust, prompts, initial/live resize, raw bytes, drain, cancellation,
session isolation and owned shutdown. See the [S01 record](2026-09-14-sshnet-s01.md).
